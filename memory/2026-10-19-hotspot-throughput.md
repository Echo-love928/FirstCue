# DEBUG REPORT — 热点数量与采集效率

- 日期：2026-10-19
- Status：DONE_WITH_CONCERNS（代码、隔离回归和生产构建完成；真实网络与付费模型的端到端耗时待恢复监控后观察）
- Symptom：用户反馈可搜索到的热点偏少、搜索较慢，要求再次适度降低筛选限制。

## Root cause

1. 旧 X 门槛要求点赞 10、转发 5、浏览 500、粉丝 100 全部满足，排除了大量已有具体内容的较早期原创。保存的近期原创样本中，按现有内容价值检查合格的候选只有 47 条。
2. 独立公开搜索等待全部 X/订阅采集结束才开始；每次搜索只深入读取前三条原文，且可读视频简介也强制读取详情，占用后续发现预算。
3. 准备分析时再次读取已具备有效原文的材料，增加等待。并发读取时原有 Throttle 在等待后才记录时间，会让同平台等待者同时发送请求。
4. 最近真实运行记录包含 AI 输出截断：耗时约 145 秒、审核 0 条；截断后直接中断整个审核流程，保存候选没有及时产出结果。

## Fix

- `shared/twitter.ts`：门槛适度下调为点赞 5、转发 1、浏览 200、粉丝 50。原创类型、数据完整性、五天时效、逐规则相关性和事实核验继续执行。保留筛选协议版本，避免因放宽门槛隐藏原有合格事件。
- `server/runner.ts`：公开发现与 X/订阅采集并行；独立发现预算占比由 60% 调为 80%；每次搜索最多深入读取六条去重原文，最多同时读取三条。有效简介及正文直接复用，额外视频指标回查最多两条并预留一次补证预算。总搜索与每日付费上限保持原设置。
- 旧门槛过滤、当前达标的 X 候选在下一轮采集或重新核实时自动恢复审核资格，不用等待重新搜到。
- AI 输出截断时按候选组拆半继续审核；推文及其关联原文保持同组，旧原文不能在拆分时丢失。成功批次分别提交，拆分失败本身不增加候选审核次数；模型日调用预算仍执行。
- `server/sources.ts`：指标回查优先级复用统一门槛；限速器提前预留同平台请求时刻，避免并发集中请求。
- README、多平台方案及 Twitter 筛选说明同步更新。
